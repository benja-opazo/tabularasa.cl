# Internationalization (English + Spanish)

## Approach: client-side dictionary swap, not per-locale pages

No build step, one `index.html` - so there's no server-side routing (`/es/`)
and no templating to generate two static pages. Instead:

- `site/assets/i18n/en.json` / `es.json` - one flat JSON object per locale,
  one key per translatable string. English is canonical; edit it first.
- `site/assets/js/i18n.js` - detects the locale (`?lang=` query param, else
  `localStorage.lang`, else `navigator.language`), fetches only that
  locale's JSON, applies it to the DOM, persists the choice, and exposes
  `window.TRI18N.t(key, vars)` / `.onChange(cb)` for other scripts
  (`downloads.js`) that build strings at runtime.
- HTML marks translatable nodes with `data-i18n="key"` (textContent),
  `data-i18n-html="key"` (innerHTML - only for the handful of strings with
  trusted inline markup, e.g. the hero's `<br>`/`<span class="accent-text">`),
  or `data-i18n-attr="attr:key[;attr2:key2]"` (element attributes - used for
  `<title>`'s sibling `<meta content>`, `aria-label`, tooltip `title`).

This mirrors the existing dark/light pattern (`theme.js`) closely enough to
keep the codebase's conventions consistent: same persistence key style, same
"detect once, follow explicit choice" logic, same toggle-button-in-header
placement.

## Why per-locale JSON files, not one shared JS file

Until this round, both locales lived in one `i18n-strings.js` as
`window.TR_I18N = { en: {...}, es: {...} }`, loaded synchronously in one
`<script>` tag. Split into `assets/i18n/<locale>.json` for two independent
reasons:

1. **Adding a locale shouldn't touch existing ones.** A new language (e.g.
   Italian) is "new `it.json` file + one entry in `i18n.js`'s `SUPPORTED`
   array" - zero edits to `en.json`/`es.json`, cleaner diffs, and a tighter
   scope for the `sync-i18n` skill (it now diffs one pair of files, not two
   objects interleaved in one file).
2. **Only the active locale needs to block anything.** Plain JSON (not
   `window.TR_I18N.xx = {...}`) is fetchable on its own, which enables the
   loading strategy below - shipping every visitor both locales' full text
   regardless of which one they'll actually see was pure waste.

## Loading strategy: active locale first, the rest in the background

`i18n.js` no longer assumes the dictionary is already in memory:

1. On load, it detects the locale and `fetch()`s just that one JSON file,
   applying it once the response resolves.
2. After the page's `load` event (so it doesn't compete with anything on the
   critical path - images, fonts, `downloads.js`'s manifest fetch), it
   background-fetches every *other* locale in `SUPPORTED` and caches each as
   it arrives. This is silent - no DOM change, just warms the cache.
3. Toggling locale (`setLocale`) applies instantly if the target is already
   cached (the common case, once the background load has finished - which in
   practice is within a second of page load). If someone toggles before that
   finishes, it fetches on demand and applies once resolved - a graceful
   one-time delay, never a broken or stuck state.

This means a full page load only blocks on ~half the total dictionary bytes
instead of all of it, while a same-session language toggle still feels instant
in the near-universal case. See "Known trade-off" below for the cost this
doesn't avoid.

**`finishApply()` runs after both the initial load and every explicit
switch** - not just switches. This matters: `downloads.js` computes some
strings via `t()` synchronously at page-load time (before the active
locale's fetch can possibly have resolved yet), so without a "first load also
counts as a change" signal, anything it computed before that fetch resolved
would stay stuck on a raw fallback key forever, not just briefly. Firing the
same `onChange` listeners on first load as on every later switch means
`downloads.js`'s existing re-render logic self-corrects for free.

## `?lang=` as a detection source, for a different-origin caller

Added when `worker/index.js`'s `/latest/<platform>` landing page started
reusing this same `i18n.js` for its header/footer/nav text
(`docs/decisions/download-redirect.md`). That page is served from
`downloads.tabularasa.cl`, a different origin from `tabularasa.cl` - it has
no access to this origin's `localStorage`, so without an explicit signal it
would only ever fall back to guessing from `navigator.language`, which can
disagree with whatever locale the visitor actually had the site in.
`downloads.js` appends `?lang=<current locale>` to every download link for
exactly this reason; `i18n.js` checks that param **before** `localStorage`
so a cross-origin link always wins over a stale local choice. No existing
page passes this param today, so the addition is inert for normal browsing -
it only activates when something explicitly sets it.

## Why this over separate `/en/` `/es/` URLs

Would give proper per-locale SEO and no flash-of-untranslated-content, but
requires either a build step (generating two HTML files from one source) or a
server-side router - both are the "no build, no framework" hard constraint
this repo runs on. If this site grows enough that bilingual SEO actually
matters, propose the build-step change here first; don't silently add one.

## Known trade-off: brief content flash

`i18n.js` runs from a `<script>` at the end of `<body>`, same place as
`theme.js`/`demo-table.js`/`downloads.js` - by the time it runs, the DOM
already has its English default text, and the active locale's dictionary is
still an in-flight `fetch()` on top of that. For a Spanish-preferring visitor
this is a brief textual flash before JS re-writes it, unlike the theme
toggle's true zero-flash (which works because colors are one attribute swap
done in a `<head>` inline script _before_ body content exists). Translating
text content can't use that trick - nodes to translate don't exist yet when a
`<head>` script would run, and now there's a same-origin fetch layered on top
of that gap too. The fetch adds a little to a flash that already existed
(same-origin JSON is typically fast enough to not matter in practice); it
isn't a new category of regression. Accepted as standard behavior for a
vanilla, build-free i18n toggle; revisit only alongside the SEO question
above.

## The showcase demo is NOT translated

`#tr-demo-root` (rendered entirely by `demo-table.js`) stays English-only,
deliberately excluded from `data-i18n` markup. It's a pixel-faithful replica
of the real Tabula Rasa app, which is English-only today
(`docs/decisions/demo-table.md`) - translating the chrome around a still-
English app would misrepresent what a Spanish-speaking user actually gets
when they download it. Revisit only once the app itself ships localization,
and then mirror its actual strings, not a fresh translation.

## Keeping `en.json`/`es.json` in sync

Both locale files must have **exactly the same key set** - `i18n.js` does not
fall back key-by-key across locales, a missing key renders literally as its
key string. The `sync-i18n` skill (`.claude/skills/sync-i18n/SKILL.md`) is
the intended workflow for adding or editing copy: edit `en.json`, run the
skill, it translates the diff into `es.json` and asks about anything
ambiguous (idiom, brand name, tone) rather than guessing.

## Inline HTML text is a fallback, and it drifts silently

Every `data-i18n` element in `index.html` / `pricing.html` also carries the
English text inline. That inline copy is **not** the source of truth -
`en.json` is - and `i18n.js` overwrites it once its fetch resolves, so a
stale inline value is invisible during normal browsing. It is still what a
non-JS crawler indexes and what shows during the pre-JS flash, so it drifted
a full copy generation before anyone noticed (the trust cards still described
an older set of guarantees, and `download.desc` still advertised a "lifetime
pass" monetization model that `en` had dropped).

When editing `en.json`, update the matching inline text too. A quick way to
find drift: walk every `data-i18n` / `data-i18n-html` / `data-i18n-attr` in
the HTML and compare the element's inner text (or the named attribute)
against `en.json`'s value for that key, whitespace-normalized and with
entities decoded - `&hellip;` vs `…` is a false positive, not real drift.
When re-wrapping a rewritten string across lines, only break at whitespace
that existed in the source string: breaking between an inline tag and the
text it hugs (e.g. `<span class="accent-text">flash</span>.`) injects a
rendered space, which shows up as a gap before punctuation.

## `<noscript>` content can never be translated

The `<noscript>` block inside `#tr-demo-root` is unreachable by `i18n.js`
either way: with JS enabled the parser treats its contents as raw text and
never builds DOM nodes for it (so `querySelectorAll('[data-i18n]')` misses
it), and with JS disabled `i18n.js` never runs at all. Its `data-i18n`
attribute is inert - the hardcoded English is what every visitor sees,
Spanish-speaking or not. Keep that string short and self-contained, and
don't put markup that matters (like a download link) only there. This is
consistent with the showcase demo being English-only anyway.
