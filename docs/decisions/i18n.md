# Internationalization (English + Spanish)

## Approach: client-side dictionary swap, not per-locale pages

No build step, one `index.html` - so there's no server-side routing (`/es/`)
and no templating to generate two static pages. Instead:

- `site/assets/js/i18n-strings.js` - `window.TR_I18N = { en: {...}, es: {...} }`,
  one flat key per translatable string. English is canonical; edit it first.
- `site/assets/js/i18n.js` - detects the locale (`localStorage.lang`, else
  `navigator.language`), applies the dictionary to the DOM, persists the
  choice, and exposes `window.TRI18N.t(key, vars)` / `.onChange(cb)` for other
  scripts (`downloads.js`) that build strings at runtime.
- HTML marks translatable nodes with `data-i18n="key"` (textContent),
  `data-i18n-html="key"` (innerHTML - only for the handful of strings with
  trusted inline markup, e.g. the hero's `<br>`/`<span class="accent-text">`),
  or `data-i18n-attr="attr:key[;attr2:key2]"` (element attributes - used for
  `<title>`'s sibling `<meta content>`, `aria-label`, tooltip `title`).

This mirrors the existing dark/light pattern (`theme.js`) closely enough to
keep the codebase's conventions consistent: same persistence key style, same
"detect once, follow explicit choice" logic, same toggle-button-in-header
placement.

## Why this over separate `/en/` `/es/` URLs

Would give proper per-locale SEO and no flash-of-untranslated-content, but
requires either a build step (generating two HTML files from one source) or a
server-side router - both are the "no build, no framework" hard constraint
this repo runs on. If this site grows enough that bilingual SEO actually
matters, propose the build-step change here first; don't silently add one.

## Known trade-off: brief content flash

`i18n.js` runs from a `<script>` at the end of `<body>`, same place as
`theme.js`/`demo-table.js`/`downloads.js` - by the time it runs, the DOM
already has its English default text. For a Spanish-preferring visitor this
is a very brief textual flash before JS re-writes it, unlike the theme
toggle's true zero-flash (which works because colors are one attribute swap
done in a `<head>` inline script _before_ body content exists). Translating
text content can't use that trick - nodes to translate don't exist yet when a
`<head>` script would run. Accepted as standard behavior for a vanilla,
build-free i18n toggle; revisit only alongside the SEO question above.

## The showcase demo is NOT translated

`#tr-demo-root` (rendered entirely by `demo-table.js`) stays English-only,
deliberately excluded from `data-i18n` markup. It's a pixel-faithful replica
of the real Tabula Rasa app, which is English-only today
(`docs/decisions/demo-table.md`) - translating the chrome around a still-
English app would misrepresent what a Spanish-speaking user actually gets
when they download it. Revisit only once the app itself ships localization,
and then mirror its actual strings, not a fresh translation.

## Keeping `en`/`es` in sync

Both locale objects in `i18n-strings.js` must have **exactly the same key
set** - `i18n.js` does not fall back key-by-key across locales, a missing key
renders literally as its key string. The `sync-i18n` skill
(`.claude/skills/sync-i18n/SKILL.md`) is the intended workflow for adding or
editing copy: edit `en`, run the skill, it translates the diff into `es` and
asks about anything ambiguous (idiom, brand name, tone) rather than guessing.

## Inline HTML text is a fallback, and it drifts silently

Every `data-i18n` element in `index.html` / `pricing.html` also carries the
English text inline. That inline copy is **not** the source of truth - `en`
in `i18n-strings.js` is - and `i18n.js` overwrites it on load, so a stale
inline value is invisible during normal browsing. It is still what a non-JS
crawler indexes and what shows during the pre-JS flash, so it drifted a full
copy generation before anyone noticed (the trust cards still described an
older set of guarantees, and `download.desc` still advertised a "lifetime
pass" monetization model that `en` had dropped).

When editing `en`, update the matching inline text too. A quick way to find
drift: walk every `data-i18n` / `data-i18n-html` / `data-i18n-attr` in the
HTML and compare the element's inner text (or the named attribute) against
`window.TR_I18N.en[key]`, whitespace-normalized and with entities decoded -
`&hellip;` vs `…` is a false positive, not real drift. When re-wrapping a
rewritten string across lines, only break at whitespace that existed in the
source string: breaking between an inline tag and the text it hugs (e.g.
`<span class="accent-text">flash</span>.`) injects a rendered space, which
shows up as a gap before punctuation.

## `<noscript>` content can never be translated

The `<noscript>` block inside `#tr-demo-root` is unreachable by `i18n.js`
either way: with JS enabled the parser treats its contents as raw text and
never builds DOM nodes for it (so `querySelectorAll('[data-i18n]')` misses
it), and with JS disabled `i18n.js` never runs at all. Its `data-i18n`
attribute is inert - the hardcoded English is what every visitor sees,
Spanish-speaking or not. Keep that string short and self-contained, and
don't put markup that matters (like a download link) only there. This is
consistent with the showcase demo being English-only anyway.
